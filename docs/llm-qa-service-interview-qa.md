# LLM QA Service 面试问答

以下答案按“先结论、再实现、最后结果/限制”的顺序组织。面试时不要一次背完整段落，先回答主问题，再根据追问展开。

## A. 项目概述

### Q1：请介绍一下这个项目。

**建议回答（约 60 秒）**

我做的是一个企业知识库问答服务。用户上传 txt、Markdown 或 PDF 后，系统会解析、切分、生成中文 embedding 并存到 PostgreSQL/pgvector；提问时先做向量和中文 BM25 混合检索，再在候选块里按事实句 rerank，最后让 OpenAI 兼容的 LLM 基于资料回答，并输出 `[资料1]` 这样的来源。除了普通 RAG，我还实现了 Agent tool calling，可以自主调用知识库、计算器和当前时间工具，也能通过 allow-list 接入 stdio 或 Streamable HTTP MCP。项目用 FastAPI、SSE、Docker、Render 和 GitHub Actions 交付，加入账号级资源隔离，58 个 pytest 覆盖主要逻辑。

**可补充结果**：31 条中文评测集；mock hybrid Hit@1 96.5%、Hit@4 100%，local bge hybrid Hit@1 100%；真实 DeepSeek 基线的关键词、引用和资料不足拒答检查均通过。

### Q2：为什么选择做 RAG，而不是微调模型？

**建议回答**

员工制度这类内容更新频繁，重点是让回答引用当前文档，而不是把知识永久写进模型参数。RAG 可以在上传新版本后重新索引，成本和迭代周期比微调低，还能保留证据片段，便于审计和排查。微调更适合改变格式、风格或稳定的任务行为；本项目的首要问题是知识注入和可追溯性，所以先做 RAG。

### Q3：从用户提问到最终回答，完整链路是什么？

**建议回答**

上传阶段是解析文件、按段落/句子切分、生成 embedding、写入 documents 和 chunks。查询阶段生成 query embedding，同时在当前知识库范围计算 BM25 候选；两路候选合并后，对每个 chunk 的事实句计算 BM25，再用 RRF 融合排名并去重。排名靠前的片段进入 RAG prompt，prompt 要求只基于资料回答、附带引用、没有依据时明确说明；FastAPI 再以完整 JSON 或 SSE 事件返回回答和来源。

## B. 检索与评测

### Q4：为什么要用混合检索？

**建议回答**

向量检索擅长语义相似，但对“二线城市”“800 元”“提交后 10 天”这类精确词和数字不一定稳定；BM25 对关键词、实体和金额更敏感。两者的原始分数范围不可直接相加，所以我先分别取候选，再用 RRF 按排名融合。候选块里还会做句级 BM25，避免“差旅报销”这样的章节标题压过真正包含金额或时限的事实句。

### Q5：RRF 为什么比直接把 cosine 和 BM25 分数相加更合适？

**建议回答**

cosine 相似度和 BM25 的量纲、分布、归一化方式不同，直接加权需要额外校准，而且换模型或语料后权重容易失效。RRF 只使用每一路的排名，能让同时被两路召回的 chunk 获得稳定提升，参数简单，也方便在同一评测集上比较。它不是万能方案，规模变大后我会考虑带中文分析器的 OpenSearch/Elasticsearch，并继续用同一评测集验收迁移。

### Q6：你怎么证明混合检索真的变好了？

**建议回答**

我先固定了 31 条版本化中文问题集，其中 29 条可回答、2 条不可回答；每条可回答题都有正确文档、原文证据和关键事实标注。检索使用 Evidence Hit@K、MRR 和 P95 延迟，不把主观 demo 当结论。当前 mock hybrid 是 Hit@1 96.5%、Hit@4 100%、MRR 0.9828；local bge hybrid 是 Hit@1/3/4 100%、MRR 1.0。CI 用 mock + hybrid 设置 Hit@1 ≥ 95%、Hit@4 = 100% 的门槛。

### Q7：Hit@K、MRR 分别表示什么？

**建议回答**

Hit@K 看标注证据是否出现在前 K 个结果里，衡量“能不能召回”；MRR 是第一条正确证据排名倒数的平均值，越接近 1 说明正确结果越靠前。例如第一名命中贡献 1，第二名命中贡献 0.5。Hit@1 适合看首条结果质量，Hit@4 更像上下文窗口的召回保障。

### Q8：为什么 CI 不直接跑真实 LLM？

**建议回答**

真实 LLM 会带来费用、网络波动、供应商限流和模型版本变化，不适合作为每次 push 的确定性门槛。因此 CI 只跑 mock embedding + hybrid 检索，验证排序逻辑和证据召回。真实 LLM 评测放在手动或定期运行，另外检查关键词、引用、资料不足拒答；可选 judge 检查忠实度，但它是辅助信号，不是绝对真值。

### Q9：LLM-as-a-judge 如何避免“看起来有分数但其实不可验证”？

**建议回答**

裁判输入同时包含问题、检索资料、人工标注和候选回答，并被明确要求忽略资料和回答中的任何指令，只返回严格 JSON：`faithful`、`answer_correct`、`refusal_appropriate`、`reason`。解析失败不会计为通过，报告会列出失败回答和理由，同时记录候选模型、裁判模型、temperature 和 prompt 版本。当前首份基线候选和裁判都用 `deepseek-chat`，所以只能说明链路稳定，不能当作独立模型的准确率；下一步可用不同模型交叉复核。

### Q10：资料不足时怎么防止模型编造答案？

**建议回答**

prompt 规定只能使用检索资料，并要求明确说明“资料不足/未明确提及”；评测也不接受只有“我不知道”这类没有知识库归因的句子。生成检查同时验证拒答表达、引用格式和引用是否指向正确证据。之前有一条回答虽然说了“资料中未明确提及”，前面却先回答了另一个相近问题，固定拒答短语规则把它误判为失败；我把规则改成更宽容的 source-grounded refusal，并在报告中列出具体失败回答，复跑 v3 后 2/2 不可回答题通过。

## C. Agent、MCP 与安全

### Q11：Agent 和普通 RAG 有什么区别？

**建议回答**

普通 RAG 通常是服务端固定先检索再生成；Agent 把检索、计算和查时间都描述成 Tool，由模型根据问题决定是否调用。调用链是“模型返回工具名和 JSON 参数 → 服务执行 → 以 tool 消息回填 → 模型继续判断”，直到最终回答或达到上限。这样能处理多步问题，但需要更严格的参数、循环和超时控制。

### Q12：为什么计算器要用 AST 白名单？

模型生成的表达式是不可信输入，不能直接 `eval`。我把表达式解析成 AST，只允许数字和受限算术节点，拒绝函数调用、属性访问、`__import__`、超大指数和过大的中间结果，并限制长度。计算本身是确定性的，也比让 LLM 心算更容易测试和复现。

### Q13：MCP 与 function calling 的关系是什么？

**建议回答**

function calling 是模型输出工具名和 JSON 参数的调用格式；MCP 是外部工具、资源和提示的标准通信协议。项目把 MCP server 暴露的工具适配成内部 Tool，因此现有 Agent loop 不需要重写。安全上 server 和 tool 都由部署者 allow-list，客户端不能提交 command、URL 或 token，并且有工具数量、调用超时和输出长度限制。

### Q14：如果 MCP server 返回恶意内容怎么办？

**建议回答**

MCP 返回值也被视为不可信数据，不把它当系统指令执行；适配器只把受限长度的文本结果作为 tool 结果回填。server、工具、命令/URL 配置由部署者控制，API 请求只能选择是否启用 MCP，不能动态指定目标。还要对工具调用次数、单次超时和总输出做上限控制。更高要求的生产环境还应增加审计、权限和网络隔离。

## D. 后端、可靠性与交付

### Q15：LLMClient 做了哪些生产化处理？

**建议回答**

我用单例 + `httpx.AsyncClient` 连接池复用连接，并设置最大连接数和 keep-alive 上限。429 尊重 `Retry-After`，5xx 和网络错误用指数退避加 jitter 重试，4xx 直接失败；流式请求只在收到响应头前重试，避免已经展示的 token 重复。配置都从环境变量读取，secret 不入 git。测试用 `MockTransport` 模拟限流、服务器错误、网络错误和流式边界。

### Q16：为什么用 PostgreSQL + pgvector，而不是单独的向量数据库？

**建议回答**

项目规模和部署目标是中小型企业知识库。会话、文档、chunk 和向量放在一个 PostgreSQL 中，可以复用事务、权限、备份和 SQLAlchemy，少维护一套服务；pgvector 已能满足当前 top-k 检索。规模明显增大或需要更强 ANN/中文词法分析时，再把向量或 BM25 迁移到专用服务，并用现有评测集做回归验收。

### Q17：你如何测试这个项目？

**建议回答**

第一层是 58 个 pytest：认证隔离、HNSW、基准参数、API、RAG、hybrid 排序、Agent 循环、MCP、LLMClient 重试和评测逻辑；第二层是 mock + hybrid 的离线 CI 门槛；第三层是配置真实 key 后的 API/前端/Render 端到端验证。测试还覆盖危险计算表达式、未知工具、坏参数、循环上限、未配置 MCP 的 503，以及评测报告中的失败回答诊断。

### Q18：项目现在还有哪些生产化缺口？

**建议回答**

当前核心链路和评测已完成，账号级登录和资源隔离也已加入，但还没有企业 SSO、部门/租户权限和管理员后台。下一步是用 Alembic 管理 schema 迁移、给清空历史增加二次确认，并用独立裁判模型做交叉复核。若知识库规模增长，还要把进程内 BM25 换成带中文分析器的专用索引，并补充可观测性、成本和权限审计。
